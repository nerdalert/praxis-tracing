Start with the routing problem

One model endpoint. Many serving pools.

Grid keeps a current view of providers across sites, applies routing policy, and gives the Gateway a versioned choice for the next request.

What Grid does

Observes provider inventory, eligibility, and supported serving signals. Computes candidates and distributes routing state.

client request→Praxis Gateway→selected pool

Why it matters

A model can exist in several pools. The best place for the next request can change as availability, pressure, and policy change.

The Gateway reads accepted state locally; it does not scrape a model on every request.

The framework in this recording

A pool can be ready and still be busy.

Each Dynamo pool has its own Frontend and Mocker. Readiness and activity answer different questions.

Can it serve this model?

dynamo_frontend_model_ready{model}

A model-scoped readiness signal. Ready does not mean idle.

How much work is active?

dynamo_frontend_active_requests

Frontend-wide active work. The demo gives each Frontend one model and compares it with a declared reference of four.

Dynamo stage gauges provide extra processing detail. They are not llm-d queues, KV-cache utilization, measured capacity, or GPU saturation. Mocker returns synthetic responses.
Real metrics: model readiness + active requests. Synthetic inference: Mocker.DYNAMO FRONTEND

THANKS FOR WATCHING
One routing interface, multiple serving frameworks

The pool behind the route can change.

This recording used Dynamo Frontend signals. A deployment can instead use llm-d and EPP signals when its adapter, model route, and policy match. Grid keeps the routing contract; signal semantics stay explicit.
